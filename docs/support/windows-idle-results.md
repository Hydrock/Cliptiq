# Простой основного приложения Windows: измерения и изменения

12 ноября 2026, ветка `performance/windows-idle`. Исходная версия:
`a9fe3bacffefed179cbfaa96024014bb7f9a3f08`. Это настоящий Cliptiq Base,
не Raven и не отдельный settings prototype. Windows11 build26200,
MSVC19.51.36247 x64, MinSizeRel, static CRT, IPO/LTO. Ryzen9 9950X3D,
32 логических CPU. macOS/Linux не измерялись.

## Результат

По30с наблюдения после5с стабилизации, отсчёты каждые5с. Числа памяти ниже —
последний отсчёт соответствующего сценария. CPU — delta всего30с интервала.
Все записи синтетические, около1KiB текста; изображений и OCR нет.

| Сценарий без видимых окон | Было: working set / private commit, MiB | Стало: working set / private commit, MiB | CPU было → стало, % одного ядра |
|---|---:|---:|---:|
| Пустая история | 20.64 / 3.39 | 12.61 / 2.38 | 1.46 → 0.31 |
| 1000 текстовых записей | 24.64 / 8.00 | 17.38 / 7.00 | 5.42 → 0.52 |
| 1000 записей, настройки открыты и закрыты | 25.40 / 8.09 | 23.50 / 7.48 | 4.95 → 0.42 |

CPU100% означает одно полностью занятое логическое ядро. На этой32-thread
машине итоговые0.31–0.52% одного ядра соответствуют примерно0.010–0.016%
общей мощности CPU, а не0.3–0.5% Task Manager. Это не нулевое потребление:
остаются периодические проверки IPC/ревизий/обслуживания. Между промежуточными
локальными прогонами значения отличались; они не являются гарантией p95 или
долгосрочным средним на всех Windows. Запуски и CPU других приложений не
контролировались; начало окончательной серии частично пересекалось с тестами.

Working set включает разделяемые страницы системных DLL. Private commit —
приватная закоммиченная память процесса, не точный private resident set.
Нельзя складывать эти две колонки или считать private commit полной ценой RAM.
Графический драйвер/системные службы отдельно не измерялись.

В отличие от первого запуска, показ настроек загружает дополнительные Win32
ресурсы; после уничтожения контролов не вся системная/heap/cache память
немедленно возвращается ОС. Закрытие HWND не обещает возврат к startup working set.

## Исправленные причины

1. Главный Windows loop использовал5ms timeout, а NativeMenu дополнительно
   ограничивал ожидание10ms. Теперь он ждёт сообщения максимум100ms, что
   сохраняет период существующего IPC polling. После обработки сообщений
   немедленно возвращает управление контроллеру, не откладывает hotkey/selection
   callbacks на100ms. MWMO_INPUTAVAILABLE учитывает сообщения, оставшиеся после
   ограниченного dispatch pass. Это не100ms безусловный sleep.
2. MediaService при каждом poll читал erase generation и будил worker даже
   без работы, а каждые250ms обходил всю неизменную историю и проверял previews.
   Теперь idle polling не будит worker, сканирование зависит от data revision;
   незавершённые порции очереди продолжаются, completions и erase checks сохранены.
3. SessionInstance::receive начинал write transaction и DELETE даже у пустого
   mailbox. Теперь пустой poll — read-only; при наличии работы повторное чтение
   и удаление остаются в одной write transaction.
4. `--background` раньше разбирался, но не применялся. Теперь Windows launcher
   создаётся скрытым, если tray доступен. Отсутствующий/отключённый tray оставляет
   видимый recovery launcher; скрытый owner HWND существует для сообщений.
5. WM_CLOSE настроек раньше лишь скрывал дерево контролов. Теперь оно уничтожается,
   borrowed handles обнуляются, следующее открытие снова читает committed settings.
   Неприменённый draft и раньше не переживал повторный show(), поэтому это не
   изменение обещания сохранения draft. Проверено повторное открытие через IPC.

Принудительное EmptyWorkingSet/SetProcessWorkingSetSize не применяется.
Искусственное вытеснение страниц уменьшает отображаемое число, но не размер
данных/commit и может ухудшить следующий отклик.

## Отдельно: снятие совместимости с Clipy

По запросу пользователя удалены XML import/export и legacy migration:
[решение](clipy-compatibility-retired.md). Убраны UI/actions/API/codec/importer,
Realm/Swift toolchain job и связанная специальная логика replay.
SQLite для собственных данных сохранена; пользовательские БД не удалялись.
TinyXML2 остаётся для Atom feed обновлений, а не для Clipy.

Чтобы не приписывать удалению совместимости чужой эффект, сначала измерена
оптимизация с прежней функциональностью: 18.64MiB working set /7.05MiB private,
0.31% одного ядра на1000 текстовых записях. Снижение CPU уже было достигнуто.
Разброс последующих memory/CPU snapshots не доказывает отдельный вклад XML.

Baseline EXE1692160B, промежуточный оптимизированный с Clipy1693184B,
финальный1649152B. Удаление совместимости уменьшило EXE на44032B относительно
промежуточной сборки; вместе с оптимизацией итоговая экономия43008B (42KiB).
Миграция раньше вообще не линковалась в приложение, её удаление не считается
экономией его runtime RAM.

Финальный portable ZIP с notices/manifest:841445B; app-owned1659099B.
Unsigned MSIX также создан, но установка/trust не подтверждены. Native closure,
inventory/architecture и relocated --version прошли штатный packaging tool.
Пакеты находятся в `out/t17-windows-x86_64-base/`, не опубликованы.
Manifest честно отмечает сборку рабочего дерева относительно исходного коммита.

## Проверка и границы

- Регрессии воспроизведены до исправлений: неизменная история повторно сканируется;
  пустой mailbox берёт write lock; background показывает launcher; Settings
  сохраняет HWND после закрытия. После исправлений проверки проходят.
- Обычный BUILD_TESTING включает новые idle_media_revision/idle_mailbox_readonly.
- Доступный набор CTest35/35 проходит. Python policy tests26, три symlink/privilege
  skips, failures0. Feature coverage и fail-closed release gate проверены;
  сняты только требования T11/T14 вслед за принятым удалением возможностей.
- **Полный набор не green:** 11 native тестов получают CreateWindowStation
  Access denied5 даже вне sandbox; positive Authenticode CRT fixture также
  не проходит. Они не подавлены и не переписаны ради зелёного результата.
  Lifecycle registry test прошёл вне sandbox с отдельным TEMP.
- Реальное приложение в обычном desktop прошло hidden startup, IPC открытия/
  закрытия/повторного открытия настроек, нормальное завершение и проверку отсутствия
  видимых окон. Это не заменяет полную native GUI-приёмку.

Замер использует отдельный LOCALAPPDATA только у child process, отдельную БД,
активный clipboard listener, но отключённое сохранение всех форматов в fixture:
личное содержимое буфера не сохраняется. Это проверка простоя, а не throughput
захвата. OCR, сеть, screenshot observation выключены. Базовая история в SQLite
не загружается целиком как payload, однако данные/меню/кэши увеличивают память.

В baseline `--background` игнорировался: стенд скрывал только собственный launcher
после его создания. Финальная версия не показывает его изначально. Поэтому
memory delta включает экономию первого видимого UI, а не только SQL-оптимизацию.
Системные caches не очищались. Все окончательные JSON сверены с SHA256 EXE.

## Дальнейший резерв

Для приближения CPU к нулю: уведомление/сигнал для Windows IPC вместо SQL poll,
явные уведомления об изменениях и completion вместо revision polling, таймеры
только на ближайшее реальное обслуживание. Такой переход нужно проверить на
потерянные wakeups, burst копирования, sleep/resume и latency горячих клавиш.

Для RAM: ленивое создание image worker, лимиты/эвикция preview cache (сейчас
его предел16MiB), освобождение чистого editor UI, измерение SQLite page-cache
budget под реальной нагрузкой. Не следует заменять SQLite самописным хранилищем
без доказательства выигрыша: весь пустой Base процесс уже имеет около2.4MiB
private commit. Крупные изображения/очереди и OCR надо бюджетировать отдельно;
число12.6MiB не является максимальным расходом приложения.
