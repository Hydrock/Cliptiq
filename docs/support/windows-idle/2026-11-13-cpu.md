## Что показало профилирование

Временные QueryThreadCycleTime-обёртки измеряли участки главного потока. В изолированном прогоне главного окна `instance.receive` занял около 45% учтённых тактов контроллера (202 454 320 из 449 324 630). Это инструментирование участков кода, не ETW stack sampling. В холодном запуске заметны затраты первичного сканирования медиа; в устойчивом простое они существенно меньше. Сырые профили лежат рядом с этим отчётом в каталоге результатов.

Два типа LAN workers проверяли неблокирующие сокеты каждые 10 мс. Теперь Windows ждёт socket readiness и отдельное событие команд/остановки. Служебные таймауты проверяются с интервалом до 250 мс; при DNS и незавершённом TLS I/O сохраняются короткие проверки. Получение данных и локальная отправка не ждут этого таймера. Сброс сетевых событий выполняется через WSAEnumNetworkEvents, как описано в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsaeventselect).

IPC использует advisory auto-reset event после фиксации запроса в приватной SQLite-базе. Пустые опросы не выполняют SQL; каждые 2 секунды остаётся резервная проверка для старых отправителей и пропущенных сигналов. При Busy проверка остаётся немедленно доступной для повтора. Сигнал не содержит команды и не заменяет проверку mailbox.

Сетевой интерфейс получает новый snapshot только при изменениях службы или видимости. При входящем сопряжении уведомление показывается и в фоне. Общая логика обновления представления изменена также для macOS; macOS-сборка здесь не проверялась. Событийное ожидание сокетов/IPC в этой правке относится к Windows.

## Сравнение на одинаковой истории

30 синтетических текстовых записей, LAN/новый захват/обновления/OCR выключены фикстурой; живой clipboard listener сохранён. Раздельные профили одинаковой структуры, последовательные запуски без сборки и CTest, прогрев по 10 секунд, по 45 секунд на режим. CPU 100% означает одно логическое ядро; машина имеет 32 логических процессора. Память — средняя по выборкам.

Рабочий стол во время сравнения недоступен интерактивной автоматизации (GetCursorPos: Access denied, чёрный снимок). Поэтому видимость главного окна подтверждена через HWND, а фактическая отрисовка на разблокированном экране не подтверждена. Этот результат не заменяет повторный замер рабочего пользовательского профиля с активным экраном. Прежние 1,95% с главным окном не воспроизвелись как устойчивый baseline; сравнивать их с новым результатом некорректно.

## Сетевой стенд

Три реально подключённые TLS-службы в одном процессе, синтетические clipboard hooks/ключи, после функционального обмена текстом/PNG/URL. Измерено 30 секунд; это суммарный расход стенда, не память основного приложения. CPU: 0,937% → 0,000% по GetProcessTimes. Ноль означает отсутствие зарегистрированного приращения за короткий интервал, а не отсутствие работы; разрешение учёта CPU ограничено. Сохранены все отсчёты и SHA-256 обеих тестовых программ.

Рабочая память основного тестового приложения практически не изменилась. Working set включает разделяемые страницы, private bytes — приватную закоммиченную память; складывать их нельзя. Это одиночные короткие локальные прогоны, не статистическая гарантия для всех машин.
